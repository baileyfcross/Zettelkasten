# Terraform Infrastructure as Code

Parent topic: [[Cloud Computing]]

Terraform organizes infrastructure work around a declarative description of the desired environment, a graph of relationships among resources, and a durable record of what the tool manages. It is therefore more than a syntax for calling cloud APIs: it is an operating model that joins design, delivery, and long-term maintenance. The five topic areas below follow that lifecycle from the execution engine through configuration design, supporting providers, deployment architecture, and production operation.

## Overview Chapter

Terraform begins with [[Terraform Core Workflow and State]], the machinery that turns configuration into controlled change. A provider makes an external API legible to Terraform, while resources represent the objects that should exist. References among those objects form a dependency graph so initialization can load the required plugins and modules, planning can compare desired, recorded, and actual state, and apply can execute the approved graph in a safe order. State is the management boundary: it records which real objects correspond to configuration addresses, while remote backends, locks, access controls, encryption, versioning, and backups make that record usable by teams. Workspaces can isolate repeated instances of the same root module, but they do not replace deliberate separation when permissions, blast radius, or control-plane availability differ.

The language and reuse layer is captured by [[Terraform HCL and Module Design]]. Resource and data blocks separate objects Terraform creates from information it reads. Input variables, local values, expressions, and type constraints transform external configuration into resource arguments; outputs expose a small contract to operators, pipelines, or downstream modules. Meta-arguments such as `for_each`, `count`, `depends_on`, provider selection, and lifecycle rules change how Terraform manages a block rather than describing the remote object itself. Modules give these elements a boundary. A strong module accepts simple, purposeful inputs, hides a coherent implementation, and returns only outputs that consumers genuinely need. Stable keys and small interfaces matter because address changes can turn a harmless refactor into proposed replacement.

Terraform's reach is broader than the major cloud providers, which is the focus of [[Terraform Utility Providers and Artifacts]]. Random and time resources can create durable generated values or model time-based transitions. External data sources and null resources provide escape hatches, but they introduce procedural behavior that Terraform cannot reason about as fully as ordinary resources. Local, template, archive, TLS, cloud-init, and DNS capabilities help produce files, packages, credentials, startup configuration, and records that infrastructure needs. These tools are useful when their outputs participate explicitly in the dependency graph. They become liabilities when they hide deployment scripts, persist secrets carelessly in state, or add provider dependencies to reusable modules without a clear contract.

The same Terraform concepts support very different hosting models, synthesized in [[Terraform Cloud Deployment Patterns]]. A virtual-machine solution commonly builds immutable images before Terraform launches them into a network, so application packaging and infrastructure provisioning remain separate stages. A Kubernetes solution normally separates the cloud control plane from cluster workloads: one root module provisions the managed cluster, and a later stage configures Kubernetes or Helm only after the cluster endpoint exists. A serverless solution removes much of the fixed infrastructure but often couples code packaging and deployment more tightly to a provider's runtime. Across AWS, Azure, and Google Cloud, the resource names and network shapes change, but the architectural questions—identity, state, artifacts, availability, and layer boundaries—remain stable.

Finally, [[Terraform Delivery and Production Operations]] treats infrastructure as a maintained system rather than a one-time build. Git-based change control makes configuration the reviewed source of truth, while formatting, validation, linting, security scanning, and saved plans create quality gates before apply. Existing environments can enter Terraform through import blocks or bulk generation, but generated code requires careful refactoring and a deliberately limited blast radius; sometimes a gradual blue-green replacement is safer than importing legacy design. Long-lived environments also require purposeful upgrades, declarative state moves, recovery plans, and operating boundaries suited to application teams, platform teams, and shared services. Terraform Cloud can centralize these workflows, and Terraform Stacks extends the idea by declaring dependencies among multiple components and deployments. The recurring principle is that code, state, and organizational responsibility must describe the same boundaries if Terraform is to remain safe under change.
