# Microservice Engineering

Microservice Engineering is the chapter-level topic for deciding when independently deployable services are justified and for designing, delivering, securing, and operating them as one distributed system. Full Notes should link to a focused child topic rather than directly to this chapter tag.

## Overview Chapter

Microservices exchange one kind of simplicity for another. A monolith keeps deployment, local calls, and transaction boundaries together, but it can make independent change and selective scaling difficult as the system and organization grow. A microservice architecture separates business capabilities into independently operated services, which gives each service a clearer change boundary and lets teams deploy or scale it without rebuilding the whole application. That benefit is conditional. Every new process boundary introduces a network interaction, a contract to evolve, operational state to observe, and data that may no longer participate in one local transaction. The central engineering question is therefore not how small a service can be, but whether a proposed boundary creates enough independent value to justify the distributed-system cost.

[[Microservice Architecture Adoption]] develops that decision. Service autonomy combines focused responsibility with independent execution, deployment, and lifecycle ownership. A service can adopt a suitable technology and scale according to its own workload, while failures can be contained rather than automatically bringing down the whole application. A modular monolith may already have clean packages and layers, yet one runtime boundary still forces common deployment and often homogeneous scaling. Extraction creates operational independence only when the new boundary owns its build, data, and lifecycle. Inside that boundary, inner architecture still separates interfaces, business rules, and persistence. Outside it, an architectural inversion makes discovery, routing, configuration, resilience, identity, telemetry, and automation explicit system mechanisms. Yet autonomy also multiplies deployment pipelines, runtime configurations, diagnostic surfaces, and cross-service failure modes. A thoughtful migration begins with a well-understood domain and extracts services where changing, scaling, or owning a capability separately solves an observed problem. Premature decomposition produces coordination overhead without removing conceptual coupling. Continuous delivery and automation are consequently architectural requirements: independent deployment is meaningful only when builds, tests, configuration, rollout, and recovery are repeatable.

The boundaries themselves are the subject of [[Microservice Boundaries and Data]]. Domain-driven design uses business capabilities, bounded contexts, and a shared language to identify places where a model can remain internally consistent. Domain-centric partitions also permit different operating targets: a catalog may need many inexpensive read replicas, while order processing may need fewer but more reliable instances. A service should own the behavior and data that implement its capability, exposing an explicit interface rather than allowing other services to reach into its database. Database-per-service and polyglot persistence reinforce autonomy, but they also replace convenient cross-table transactions with duplicated data, events, and eventual consistency. The CAP constraint makes that replacement a business decision during a network partition: remain available with a temporary inconsistency, or refuse work until a consistent result can be guaranteed. Two-phase commit coordinates a stronger decision across resource managers but costs extra round trips, longer locks, and more difficult failure recovery. BASE divides the wider operation into asynchronously propagated local transactions, while a saga records a workflow and runs semantic compensations after failure. None of these mechanisms removes the need to specify acceptable intermediate states. Over-segmentation scatters one capability across many services and makes ordinary work network-bound; under-segmentation leaves unrelated reasons for change together. A defensible boundary balances cohesive business meaning, team ownership, data authority, and the cost of coordinating operations that cross it.

Once boundaries exist, [[Microservice Communication and Resilience]] governs how they collaborate. Synchronous calls provide an immediate response and straightforward request flow, but make the caller wait and can propagate latency or failure through a call chain. Asynchronous HTTP can release the request worker while a slow operation completes, improving concurrency without increasing the downstream service's capacity. Brokered messaging separates producer availability from consumer availability and can persist work or buffer spikes. A correlation identifier reunites separate requests and replies, while durable delivery, unique transaction identifiers, and sequence or version information help consumers survive loss, duplication, and reordering. Idempotence prevents one logical message from having its effect twice; it does not by itself decide whether two distinct messages arrived in the right order. Compact schema-driven encodings such as Protocol Buffers can reduce transport and marshaling work, provided schema evolution remains compatible. Service discovery maps logical service identities to changing instances; client-side load balancing selects among those instances; and centralized configuration keeps environment values outside service packages. An API gateway can route, aggregate, authenticate, cache, and throttle external requests, while a backend for frontend can tailor that gateway role to a client type. Sidecars can supply common operational behavior beside application containers. Resilience patterns such as circuit breakers, retries, timeouts, bulkheads, and fallbacks limit how dependency failure spreads, but each needs thresholds and behavior matched to the service contract.

[[Ports Adapters and Onion Architecture]] gives the service's internal boundary a matching structure. Ports state how the application core can be driven or which external behavior it requires, while adapters translate REST, GraphQL, database, remote-client, or messaging technology into those contracts. Driving adapters initiate a use case; driven adapters implement an output required by it. Onion architecture adds an inward dependency direction: infrastructure and application services surround domain services and entities, and the center does not depend on the outer technology. This allows PostgreSQL to be replaced with MongoDB or an HTTP entry port to be joined by GraphQL without rewriting the business core.

[[Spring Microservice Application Architecture]] makes those roles concrete in Java. Spring Boot creates the independently runnable process; REST controllers and GraphQL resolvers act as driving adapters; Spring Data repositories act as persistence ports whose implementations can target MongoDB or PostgreSQL; and RestTemplate or OpenFeign clients implement outgoing service calls. OpenFeign can be combined with Spring Cloud LoadBalancer to choose among discovered provider instances and with a circuit breaker to fail fast or invoke a defined fallback. Spring Cloud Config Server externalizes versioned environment configuration, which reduces drift but becomes an availability and security dependency in the outer architecture. HATEOAS responses advertise state-dependent transitions, while HAL gives links and embedded resources a regular representation. Spring's dependency injection supplies the concrete adapters, but the architectural value comes from keeping their transport and storage details at the boundary.

[[Kafka Microservice Request Reply]] shows how an asynchronous transport can support a caller that still needs a response. A request carries a return address and correlation identifier, and a reply listener completes the matching pending operation. Keys or explicit partition selection determine routing and per-partition order; consumer concurrency cannot exceed useful partition ownership, and one consumer instance is not shared among threads. When several providers answer one request, an aggregating template collects correlated replies until a completion count or timeout releases the result. Partial replies bound waiting but turn completeness into an explicit business decision.

Independent services also need independent evidence of correctness. [[Microservice Testing Deployment and Scaling]] connects isolated unit tests to integration tests, end-to-end flows, and consumer-driven contract tests. Unit tests give fast feedback about local behavior; integration tests exercise framework and dependency boundaries; end-to-end tests check a small number of critical workflows across services. Contract tests verify that a provider and its consumers agree on request and response shapes without requiring every service to be deployed together. Containers package a service and its dependencies, while Kubernetes Deployments, Services, probes, and autoscaling manage replicas. Horizontal scaling adds instances instead of enlarging one instance, so statelessness, load distribution, and downstream capacity matter. Liveness and readiness answer different questions: whether a container should be restarted and whether a pod should receive traffic. Availability targets must cover the entire request chain: 99.9% permits hours of annual downtime, while five nines permits only minutes, so each added nine requires redundancy and tested failover across DNS, networks, gateways, services, brokers, and data stores rather than extra replicas at only one layer.

Distribution makes operational evidence and trust boundaries first-class concerns, addressed by [[Microservice Security and Observability]]. Tokens can carry client identity and authorization context, while TLS and mutual TLS protect service-to-service communication and authenticate endpoints. Network segmentation, gateway controls, rate limits, key rotation, and least-privilege authorization reduce the blast radius of a compromised component. Centralized, structured logs need service, environment, request, and correlation context so one transaction can be reconstructed across ephemeral instances. Distributed traces connect spans across calls; metrics expose rates, errors, latency, saturation, and health; dashboards interpret those signals; and alert rules turn selected conditions into action. Observability must be designed with the architecture because missing context, sensitive data in logs, unbounded labels, or noisy alerts can make abundant telemetry less useful rather than more useful.

[[Helidon Microservices Framework]] shows how one Java runtime packages these architectural concerns into two programming models. Helidon SE uses explicit functional builders for servers, clients, configuration, data, and security, while Helidon MP uses MicroProfile and selected Jakarta standards with annotations and dependency injection. Both run as standalone services on Helidon's virtual-thread server. Configured routes, database statements, security providers, metrics, fault-tolerance policies, and health endpoints make service boundaries and operational behavior concrete without requiring an external application server.

These topics form one feedback loop. Business boundaries determine data ownership and communication paths. Communication paths determine failure modes, security controls, and the tests needed to protect contracts. Deployment and scaling change which instances exist, making discovery, health checks, and telemetry necessary. Production evidence then shows whether a boundary is too chatty, a dependency too fragile, or an autoscaling rule too slow. Microservice engineering succeeds when teams use that evidence to revise boundaries and operational practices, not when they maximize the number of services.
