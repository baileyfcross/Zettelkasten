# Networked Game Programming

Parent topic: [[Game Programming]]

Networked Game Programming is the chapter-level topic for transporting, synchronizing, scaling, securing, and operating a shared game across multiple computers. Full Notes should use one of the focused child topics below rather than this chapter tag.

## Overview Chapter

A networked game extends the ordinary game loop across machines that do not share memory, a clock, or a perfectly reliable communication channel. Each participant acts on a local view while messages take time to arrive, can arrive in a different order, or may never arrive at all. The central engineering problem is therefore not merely sending bytes. It is deciding what those bytes mean, which machine may make each decision, how recipients reconstruct shared state, and what the game should do when reality diverges from the ideal protocol.

[[Game Network Transport and Serialization]] forms the lowest application-facing layer. Internet Protocol addresses hosts and routes packets, transport ports identify processes, and sockets expose UDP or TCP communication to the program. TCP supplies a reliable ordered byte stream, while UDP supplies independent datagrams without built-in delivery guarantees. A real-time game chooses between them according to the meaning and lifetime of its data: a missing account transaction may be unacceptable, while retransmitting an obsolete movement sample can be worse than losing it. Network address translation complicates direct peer connections because unsolicited inbound packets lack a router mapping, so traversal techniques enlist a known third party or explicit router configuration. Once a route exists, serialization turns structured game data into a portable sequence of bytes or bits. Endianness, pointer values, padding, and platform-dependent layouts make raw memory copies unsafe; an explicit stream format gives both endpoints a stable contract.

[[Multiplayer Replication and Topologies]] determines how those messages become a shared world. A client-server design concentrates authority in one server and makes clients send requests or inputs to it. A peer-to-peer design distributes communication and can let every peer run the same deterministic simulation. The topology changes bandwidth, latency, trust, and recovery costs. Replication adds another layer by assigning network identities to objects and defining create, update, and destroy actions. Full snapshots are simple but scale poorly, so practical systems transmit world-state deltas and sometimes only the properties that changed. Remote procedure calls carry discrete events or requested operations through the same serialization machinery. Deterministic lockstep takes a different route: peers exchange commands, delay their execution until every participant has the required turn data, and use synchronized pseudo-random sequences and checksums to detect divergence.

Even a correct topology must cope with the physical network. [[Multiplayer Reliability and Latency Compensation]] distinguishes delay from variability and loss. Round-trip time measures a message-and-response path, while transmission, propagation, processing, and queuing contribute different portions of network delay. UDP-based games can attach sequence numbers, acknowledgments, and in-flight records to discover whether packets arrived. The application then decides what recovery is useful; current state can supersede a lost update instead of blindly replaying stale data. Controlled simulation of delay, jitter, and packet loss makes those decisions testable before deployment. At the presentation layer, client-side interpolation renders between known samples, prediction estimates a more current state, and move replay reapplies local inputs that the server has not yet acknowledged. Server-side rewind temporarily evaluates an action against the world the shooter saw, improving responsiveness at the cost of potentially surprising the target.

As player and object counts grow, [[Multiplayer Scalability and Security]] narrows both computation and trust. Interest management determines which objects are relevant to each client by distance, zone, potential visibility, or another game-specific relationship. Server partitioning divides simulation work, instancing creates separate copies of crowded spaces, and replication priority and frequency ration limited bandwidth. The same principle of selective disclosure improves security: a client cannot extract hidden information that it never receives. Every requested action still requires validation against authoritative state because a malformed or impossible command can arise from cheating, delay, or stale knowledge. Encryption and authentication protect sensitive traffic from interception, cheat detection can identify known hostile software, and fuzz testing exposes server code to malformed packets before attackers do. Security is therefore an architectural property of authority, information flow, validation, and operations rather than one isolated filter.

[[Multiplayer Services and Dedicated Hosting]] connects the running protocol to the broader player and server lifecycle. Gamer services supply identities, lobbies, matchmaking, relay transport, statistics, achievements, leaderboards, and other shared platform features. A lobby gathers participants before the game selects a server or begins peer communication; matchmaking turns player and session constraints into that grouping. Service-specific calls should sit behind an application abstraction so a later platform port does not force service details through the whole codebase. Dedicated hosting moves authority away from a participating player and can improve bandwidth, availability, fairness, and copy protection, but it introduces ongoing cost and operational complexity. A server fleet needs processes that launch game instances, machine-local managers that monitor those processes, and higher-level managers that place work on existing or newly provisioned virtual machines. Health reports, capacity thresholds, and cautious scale-up and scale-down rules keep the fleet responsive without creating waste during short traffic spikes.

These five topics form one dependency chain. Transport conveys serialized meaning; topology assigns responsibility for that meaning; replication reconstructs the shared world; reliability and compensation keep that world playable under imperfect timing; scaling limits work to what matters; security limits trust to what can be verified; and services plus hosting carry a session from player discovery through managed execution. A robust networked game makes each boundary explicit so that a change in packet format, authority, latency policy, relevance rule, or hosting provider does not silently change the rules of play.
