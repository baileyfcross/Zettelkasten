# Microsoft Foundry AI Platform

Microsoft Foundry AI Platform is the chapter-level topic for designing, governing, deploying, evaluating, and operating enterprise AI applications and agents in Microsoft Foundry. Full Notes should link to one of the focused child topics rather than directly to this chapter tag.

## Overview Chapter

Microsoft Foundry treats an AI application as a governed production system rather than a model endpoint with a user interface. [[Microsoft Foundry Platform Architecture]] establishes that system's administrative foundation. A top-level Foundry resource acts as the control plane for networking, identity, security policies, and shared service connections. Projects sit beneath it as isolated engineering workspaces for models, agents, workflows, knowledge, evaluations, and deployments. Resource-level controls flow into projects, allowing platform administrators to govern shared infrastructure while project teams work within bounded environments. The portal's Discover, Build, and Operate areas then organize the lifecycle from asset selection through development and production management.

[[Microsoft Foundry Data and Model Design]] covers the two inputs that most strongly shape application behavior: knowledge and model capability. Static files can live in connected storage, searchable material can be indexed through Azure AI Search, and live systems can be exposed as tools through the Model Context Protocol. Retrieval-augmented generation uses indexed evidence to ground an answer without placing enterprise knowledge permanently in model parameters. Model selection must also consider modality, context window, knowledge cutoff, safety posture, data residency, latency, throughput, cost, and customization support. Leaderboards and side-by-side comparison provide evidence, but governance requirements filter the candidate set before performance decides among acceptable models. Prompt engineering is generally the first customization technique; fine-tuning is justified only when examples and instructions cannot reliably establish the required behavior.

[[Microsoft Foundry Workflows and Deployment]] turns model capability into explicit business behavior. A Foundry workflow places model calls, transformations, tool invocations, conditions, and human review into a visible execution graph. Structured outputs are parsed before they drive branches, preventing prose variation from becoming an unsafe control signal. Agents and workflows have complementary roles: an agent interprets a user's intent and presents the experience, while a workflow defines repeatable routing and policy logic. Deployment choices follow workload constraints. Serverless endpoints favor low-volume experimentation but can introduce cold starts; real-time managed endpoints keep capacity warm for latency-sensitive applications; batch inference suits large noninteractive workloads; and workflow endpoints expose an entire orchestrated process through one contract. Versioned staging and production assets preserve a rollback path when prompts, models, tools, or workflow logic change.

[[Microsoft Foundry Evaluation and Monitoring]] provides the evidence required to decide whether that behavior is acceptable and remains acceptable. Evaluation runs bind a defined dataset, target deployment, evaluators, and thresholds into a reproducible record. Relevance, groundedness, coherence, intent resolution, task adherence, safety, and tool-call accuracy measure different failure modes, so teams select metrics that reflect the use case rather than enabling every available evaluator. Aggregate scores must be supplemented with category and sample-level review because an acceptable mean can hide severe failures in escalation or security cases. After deployment, operational metrics track traffic, latency percentiles, errors, token use, and tool reliability, while continuous or scheduled evaluations monitor behavioral quality. Scheduled red teaming deliberately probes adversarial weaknesses that normal traffic may not reveal.

[[Microsoft Foundry Responsible AI Controls]] connects broad principles to enforceable practice. Fairness, reliability and safety, privacy and security, transparency, and accountability influence data, prompts, access, evaluation, and incident response. System scope is expressed through layered prompts and clear refusal or escalation paths. Guardrails enforce runtime boundaries at input and output intervention points, while blocklists add deterministic controls for organization-specific terms or patterns. Safety filters and policies are not substitutes for workflow design: policies state expectations, guardrails enforce chosen controls, and human owners interpret signals and approve changes. False positives must be measured and calibrated by category so safety does not quietly make legitimate work impossible.

[[Microsoft Foundry Enterprise Agent Integrations]] applies these principles to assistants connected to organizational data. A production assistant begins with an explicit scope, trusted sources, success criteria, and prohibited actions. Its system prompt acts as a behavioral contract, and its tool instructions specify when a data call is required, which identifier must be present, what arguments may cross the boundary, and how empty or failed results are handled. Foundry IQ supports governed document retrieval, Microsoft Fabric Data Agents expose structured enterprise data with row-level controls, and Databricks Genie can be connected through MCP. Identity passthrough and published-agent managed identities keep authorization outside prompt text. Schema inspection, tool-call evaluation, tracing, runbooks, and limited initial rollout address the failures that arise after the connector appears to work.

Across all six topics, the recurring discipline is explicitness. Administrative scope, data access, model choice, orchestration, release criteria, runtime boundaries, ownership, and recovery behavior are made visible and testable. A fluent response is not evidence that an application is correct, safe, authorized, or operable. Production readiness comes from joining model intelligence to conventional engineering controls: least privilege, versioning, structured interfaces, representative tests, monitoring, change review, and practiced incident response.
