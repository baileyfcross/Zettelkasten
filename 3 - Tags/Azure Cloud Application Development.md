## Overview Chapter

Azure application development combines managed infrastructure with application code, but the central design problem is still the movement of information. Data must be stored, messages must be delivered, users and services must be identified, workloads must be packaged, and results must return through an interface. The Azure services described here address different parts of that path. They are most useful when their boundaries remain explicit: a database is not a message broker, a workflow is not an identity provider, and a container platform does not remove the need to design the service inside the container.

### Managed data and real-time communication

[[Azure Cosmos DB Applications]] begins with persistent application data. Azure Cosmos DB is a managed document database designed to distribute data across regions and expose it through several compatibility APIs. A document-oriented model stores records in structures that can evolve without requiring every item to share a rigid relational shape. The service can replicate those records geographically, and multi-region writes can place write capability closer to users in more than one region. Distribution improves reach and resilience, but it also makes partitioning, consistency, throughput, and conflict behavior architectural decisions rather than incidental configuration.

Before selecting a particular managed database, [[Cloud Data Storage Selection and Consistency]] asks what guarantees and access patterns each part of the application actually needs. Relational storage provides structured schemas, referential constraints, and transaction isolation, while document and other NoSQL stores often make distributed writes and flexible records easier by accepting different consistency or query tradeoffs. Redis offers a fast in-memory key-value model, disk storage favors durable local data, and a cache should not silently become the authoritative store without a recovery plan. Polyglot persistence chooses a store per bounded need, which improves fit only when the system also accepts the operational cost of several technologies and explicit movement between their consistency boundaries.

The book's project uses Cosmos DB through its MongoDB-compatible API. That choice lets a .NET application use the MongoDB driver and repository-style CRUD operations while Azure supplies the managed backing service. Compatibility is a boundary, not an identity: the application's programming model resembles MongoDB, while account configuration, provisioning, billing, and global distribution remain Cosmos DB concerns. Collections group documents, and a partition key helps the service distribute data and requests. Provisioned throughput is described in request units, so query shape and access patterns affect both performance and consumption. A sound repository hides repetitive driver operations from callers without hiding the database characteristics that determine whether those operations scale.

Stored state becomes interactive through [[Azure SignalR Service Applications]]. SignalR gives a server a persistent communication path to connected clients, allowing the server to push an event rather than making every browser repeatedly ask whether something changed. A hub defines the methods clients can call and the messages the server can send. Client handlers attach behavior to named messages, while connection setup establishes the hub route and lifecycle. In the chat project, a message received by the hub can be broadcast to all connected clients, and a JavaScript client can update the interface as soon as that broadcast arrives.

Azure SignalR Service moves much of the connection fan-out from the application host into a managed service. The ASP.NET Core application still defines hubs, messages, and authorization decisions, but the service helps maintain large numbers of client connections. Registration and connection configuration connect the application to that managed backplane. This separation is valuable only when message contracts remain clear: the client and server must agree on method names and payload shapes, and the application must decide what should happen during connection loss, reconnection, duplicate delivery, or an unavailable service.

### Workflows, functions, and identity boundaries

[[Azure Logic Apps and Functions]] coordinates work that spans services. A Logic App is a workflow made from a trigger followed by actions. A recurrence trigger starts work on a schedule; an HTTP or service event can start it in response to outside activity. Conditions choose among paths, and a for-each operation repeats an action over a collection. The visual designer makes these stages visible, which is especially helpful when the workflow integrates systems owned or operated separately.

An Azure Function supplies code at a focused step of that workflow. An HTTP-triggered function accepts a request, performs its small unit of application logic, and returns a response that the Logic App can use in later stages. This is a serverless operating model: the platform manages the host and can scale execution according to demand, while the developer supplies the function and its configuration. The boundary between workflow and function should follow responsibility. Orchestration, connectors, branches, and scheduled triggers fit naturally in the workflow; calculation or transformation that benefits from ordinary code fits naturally in the function. Their JSON request and response shapes then become an integration contract that needs validation and stable error handling.

Cross-service calls also need an identity model. [[OAuth 2.0 and IdentityServer]] separates authentication from authorization. Authentication establishes who a subject is; authorization determines what that subject may do. OAuth 2.0 provides a protocol for obtaining and presenting delegated access tokens. A client requests access for defined resources and scopes, the authorization service issues a token under an allowed grant, and an API validates the bearer token before accepting the request. Roles or claims can then support more specific authorization inside the application.

IdentityServer supplies these protocol endpoints and configuration within the .NET project. Clients, resources, scopes, users, grant types, and signing credentials describe the trust relationship. The resource-owner password flow shown in the project illustrates token exchange directly, but it also concentrates credential handling in the client and should be understood as a constrained historical example rather than a universal default. Whatever flow is chosen, an access token is not meaningful merely because it is present: the receiving API must validate its signature, issuer, audience, lifetime, and relevant authorization claims.

### Durable storage and asynchronous services

[[Azure Blob and Queue Storage]] covers two complementary storage patterns. Blob storage keeps unstructured binary objects such as files, images, archives, or logs. A storage account supplies the service boundary, a container groups blobs, and a block blob stores content assembled from blocks. Applications use a connection string and client library to create containers, upload and download data, and inspect object metadata. Access tiers such as hot and cold reflect different access-frequency and cost assumptions, while redundancy choices describe how copies are maintained against hardware or regional failure. These settings are part of the data's lifecycle and recovery design, not mere labels.

Queue storage keeps messages rather than files. A producer places a small message on a queue, and a worker retrieves it for later processing. That time separation prevents the producer from having to wait for the full downstream operation. It also changes the failure model: a worker may stop after reading a message, a message may become visible again, and several workers may compete for work. Consumers should therefore make processing safe to retry and record enough context to diagnose failures. Azure Storage Explorer provides an operational view of accounts, containers, blobs, and queues, which helps verify what the application has actually stored or enqueued.

Those mechanisms support [[Containerized Microservice Architecture]]. A microservice owns a focused business capability and can be developed or deployed with a degree of autonomy. Splitting an application this way introduces network calls, independent failure, distributed logging, and the inability to rely on one local database transaction across every service. Queue-based work distribution can reduce temporal coupling: an ordering service records or enqueues work, and a separate processor completes it asynchronously. This improves isolation and allows worker capacity to change independently, but it demands explicit message schemas, retry behavior, idempotency, and observability.

Docker packages a service and its runtime dependencies into an image. A Dockerfile describes how to build that image, and a container runs an isolated instance of it. Linux containers provide a consistent execution environment across a developer machine and a compatible host. Packaging prevents many dependency mismatches, yet it does not automatically produce good service boundaries or durable state. Images should remain reproducible, configuration should enter through controlled environment-specific mechanisms, and logs should leave the container for aggregation. The container is the unit of deployment; the service contract and its data remain the units of system design.

### Orchestration and intelligent interfaces

[[Azure Kubernetes Service Operations]] manages containers when the application requires more than a single manually operated instance. A Kubernetes cluster contains nodes that supply compute. Pods hold one or more closely related containers, deployments describe the desired application state, and replica counts state how many instances should run. Kubernetes continually compares that desired state with observed state, replacing failed pods and distributing traffic through service and load-balancing mechanisms. Azure Kubernetes Service provides a managed Kubernetes control plane, while Azure Container Registry stores the images the cluster will run.

This declarative model changes operational work. Instead of starting an individual process and hoping it stays alive, the operator declares an image, configuration, replicas, and exposure policy. Self-healing then restores instances, but it cannot decide whether an application response is semantically correct or whether a dependency has corrupted data. Health signals, resource settings, secret management, rollout strategy, and centralized logs are still required. Kubernetes improves the control loop around the workload; it does not replace application-level reliability.

The user-facing edge of the system can call specialized managed models through [[Azure Cognitive Vision Applications]]. Azure Cognitive Services exposes pretrained machine-learning capabilities through service endpoints. The Face API project sends image data to an endpoint using an access key and receives structured results such as emotion confidence scores. A pretrained service removes the need to collect a training set and operate a custom model for a common task, though the application still has to interpret confidence values carefully and handle ambiguous or failed results.

In the Xamarin.Forms client, a media plugin obtains an image from the device camera or gallery. Platform projects declare the permissions required for that native capability, while shared code sends the image to the service and presents the response. The sequence crosses several trust boundaries: the user grants camera access, the application handles biometric-like image data, a network request transmits it, and a remote model produces an uncertain inference. Good design makes permission, privacy, transport failure, endpoint configuration, and the limits of the model visible rather than presenting a score as unquestionable fact.

Conversational access builds on similar boundaries in [[Microsoft Bot Framework Applications]]. The Bot Framework represents user interactions as activities arranged into conversation turns. An echo bot demonstrates the basic loop: receive an activity, inspect its text, and send a response. The emulator lets a developer inspect that exchange locally, including the raw activity payload and conversation transcript. More capable bots can map an identified intent to a response entry, invoke application services, and preserve suitable conversational state.

Language understanding is supplied by a related child topic, [[Natural Language Understanding Systems]]. A LUIS application groups example utterances under intents, trains a model, and publishes an endpoint that predicts which intent best matches new text. The bot can use that prediction to select an action or response. As with vision scores, the prediction is uncertain and should have a fallback when confidence is inadequate or the utterance lies outside the model's learned categories. Bot registration then connects the hosted application to channels. App credentials identify the bot to the service, Direct Line supports a custom client, and Web Chat supplies a browser-oriented channel. A UWP application can wrap the same channel through its API, showing how one bot service can serve several interfaces without duplicating its conversational core.

### Architecture roles connect strategy to implementable views

[[Azure Architecture Practice and Cloud Strategy]] treats architecture as a collaboration among scopes rather than a single job title. Enterprise architects align the whole technology landscape with business direction, domain architects own a broad field such as cloud, and solution architects assemble building blocks around a particular business outcome and its non-functional requirements. Data, security, infrastructure, platform, application, and technical architects then contribute deeper views whose boundaries overlap without becoming interchangeable.

Azure architecture maps support that collaboration by organizing a domain into concerns, alternatives, possible solutions, and explicit trade-off points. A map is a decision aid rather than an approved-product list: its branches show where questions arise, not which leaf must always be selected. This preserves the distinction between an enterprise principle, a reference architecture, a platform standard, and a workload-specific choice.

### Workload models keep a reference architecture tied to intent

[[Azure Solution Architecture and Workload Models]] classifies services by the role they play in a system. Systems of engagement provide channels to people, systems of record hold authoritative state, systems of insight analyze historical data, systems of intelligence support near-real-time decisions, and systems of integration connect otherwise separate applications. These categories make it easier to challenge a design in terms of responsibility instead of comparing unrelated products.

Monitoring, delivery factories, identity, security, networking, and governance cut across every workload category. The source recommends staging these non-functional concerns through maturity levels and a roadmap instead of pretending every control can reach its final state on day one. A target reference architecture should trace business keywords to building blocks, add the relevant cross-cutting views, and record gaps that remain. It must also acknowledge service retirement so a diagram does not become a permanent claim about an evolving platform.

### Networks and recovery expose failure and trust boundaries

[[Azure Network and Resilience Architecture]] begins with hybrid connectivity and hub-and-spoke topology. ExpressRoute provides private connectivity with planned bandwidth and resilience; VPNs use encrypted tunnels over public networks. A hub can centralize shared routing, DNS, and inspection, while a double-hub design separates internet ingress from hybrid connectivity to reduce duties and blast radius. Virtual WAN secured hubs, routing intent, Route Server, and Virtual Network Manager automate different portions of route distribution and policy.

Private Link places a private endpoint for a managed service inside a virtual network, which changes both routing and name resolution. DNS Private Resolver and private DNS zones bridge Azure and on-premises domains without exposing a public path. Availability and disaster recovery then require explicit objectives: RTO and RPO state acceptable recovery targets, while RTA and RPA record what an exercise or outage actually achieved. Multi-region designs add failover and data-replication complexity, so “two regions” is not itself a complete resilience plan.

### Container selection is a management-boundary decision

[[Azure Container Platform Selection]] compares Azure Container Instances, Web App for Containers, Function containers, Red Hat OpenShift, Container Apps, and AKS by built-in behavior and operational work. ACI suits isolated or short-lived containers; App Service offers a managed web-hosting model; Function containers package an event-driven runtime; OpenShift supplies an opinionated enterprise Kubernetes platform; and Container Apps exposes serverless microservice and event-driven capabilities over managed Kubernetes foundations.

Architecture style and quality attributes matter more than the presence of a container image. Microservices, service-oriented systems, N-tier applications, event-driven processing, and resource-intensive batch jobs need different combinations of networking, autoscaling, deployment control, state, and observability. Container Apps integrates revisions, KEDA, and Dapr while hiding most cluster administration. AKS or OpenShift exposes more control but transfers more lifecycle, isolation, policy, and platform-engineering work to the customer.

### Cloud-native applications use platform capabilities as code-level boundaries

[[Azure Cloud-Native Application Architecture]] broadens development beyond application source code to identities, deployment, configuration, diagnostics, and managed service behavior. Managed identities remove stored Azure credentials; system-assigned identities follow one resource’s lifecycle, while user-assigned identities can be shared. Workload identity federation exchanges an external issuer’s token for an Entra token without distributing a client secret.

API Management centralizes API versioning, products, policies, validation, throttling, and transformations. App Configuration separates runtime settings from deployment artifacts, while Key Vault references let supported services resolve secrets without custom retrieval code. Service Bus topics and subscription filters distribute one message to selected consumers. These conveniences reduce custom plumbing only when their policies, message metadata, retry behavior, permissions, and failure modes remain part of the application design.

### Data platforms separate ingestion, computation, and consumption

[[Azure Data Platform Architecture]] maps ingestion, processing, raw storage, serving, and visualization to distinct capabilities. Event Hubs and IoT Hub ingest high-volume streams, Stream Analytics performs managed near-real-time transformations, Data Explorer specializes in fast telemetry analysis, and Databricks or Synapse spans several analytical workloads. The service boundary should follow latency, data shape, skill set, governance, and workload scale rather than a desire to standardize every stage on one engine.

Lambda architecture maintains batch and speed paths, while Kappa emphasizes streaming and a serving layer. Medallion architecture moves data through increasingly refined bronze, silver, and gold representations. Hybrid transactional/analytical processing instead asks whether live operational data can serve analytics without a duplicate pipeline; Synapse Link for Cosmos DB is the source’s Azure-native example. Each pattern changes freshness, replay, consistency, transformation ownership, and the number of stored copies.

### AI architecture separates knowledge, action, and model access

[[Azure AI Application Architecture]] connects foundation models to application data and tools. Embeddings encode semantic similarity, vector stores retain those representations, and hybrid search combines vector relevance with keyword matching. Retrieval-augmented generation supplies selected external context to a model, cache-augmented generation keeps a smaller body of knowledge directly in prompt context, and tool-augmented generation lets a model request actions through described functions.

Agentic systems add planning and autonomous task execution, which makes tool permissions, state, observation, and human approval more important. An AI gateway built with API Management shields model endpoints and can apply token validation, load balancing, rate limits, model routing, semantic caching, and message logging. The gateway governs access and consumption; it does not determine whether a generated answer or selected action is correct.

### Security joins identity, posture, workloads, and response

[[Azure Security Architecture and Operations]] treats identity as a central cloud perimeter while retaining layered network and data controls. Conditional Access evaluates contextual signals, Privileged Identity Management makes elevated roles temporary, and Continuous Access Evaluation lets aware applications react to critical identity events before a token’s normal expiry. Data protection distinguishes Microsoft-managed keys, bring-your-own-key control, hold-your-own-key custody, and key-encryption-key hierarchies; Purview adds cataloging, lineage, and broad governance.

Cloud Security Posture Management evaluates configuration and compliance before an attack, whereas Cloud Workload Protection detects threats in running resources. Defender for Cloud participates in both areas through different plans, and Microsoft Sentinel aggregates security data into SIEM and automates response as SOAR. DevSecOps moves scanning, policy, approvals, and quality gates into the delivery workflow. Azure Firewall TLS inspection can expose encrypted application traffic to controls, but it requires callers to trust a private certificate authority and adds performance and compatibility costs.

### Microsoft Entra makes identity an operational control plane

[[Microsoft Entra Identity and Authentication]] develops the identity boundary behind those security controls. Entra ID represents users, groups, applications, devices, and roles in a tenant, then separates proof of identity from permission to act. Passwordless methods, multifactor authentication, single sign-on, and Conditional Access strengthen or condition authentication, while protected actions and administrative units narrow when and where administrative authority applies. Hybrid identity and managed domain services provide transition paths for organizations that still depend on on-premises directories or legacy protocols, but those bridges should be treated as explicit dependencies rather than permanent cloud assumptions.

[[Microsoft Entra Governance and Protection]] addresses what happens after an identity exists. Entitlement Management packages resources and approval rules; Access Reviews retest whether assignments remain justified; Lifecycle Workflows automate joiner, mover, and leaver events; and Privileged Identity Management turns powerful roles into monitored, time-bound activations. Identity Protection adds risk signals and automated remediation, while workload identities extend governance to applications, service principals, managed identities, and AI agents. Monitoring, backup, emergency access, and staged migration make the identity system recoverable as well as restrictive. Together these controls treat access as a changing relationship that must be granted, observed, reviewed, and removed.

[[Microsoft Entra External and Network Access]] carries that model across organizational and network boundaries. Verified ID uses issuer-holder-verifier relationships for selective credential disclosure. External ID separates partner collaboration in workforce tenants from consumer journeys in external tenants, with cross-tenant settings defining which trust claims and resources may cross a boundary. Global Secure Access joins identity, device, and network signals: Internet Access protects web and Microsoft-service traffic, while Private Access provides application-level reachability to internal resources. Universal Conditional Access can therefore govern network traffic and legacy applications that do not implement modern authentication themselves, connecting Zero Trust policy to the actual path a request takes.

### One cloud system, many explicit contracts

These services form a coherent application only through their contracts. Cosmos DB stores durable documents; SignalR delivers immediate events; Logic Apps and Functions coordinate discrete steps; OAuth and IdentityServer govern access; blobs retain large objects; queues separate producers from workers; containers package services; Kubernetes maintains desired runtime state; and cognitive or bot services provide specialized interfaces. Substituting one role for another usually creates hidden coupling—for example, treating a database as a transient event channel or assuming a container restart is a complete recovery strategy.

The 2019-era projects also demonstrate a durable way to reason about managed cloud platforms. Every convenience transfers an operational responsibility to the provider, but none transfers the application's intent. The provider can replicate a database, maintain connections, schedule a function, run a container, or host a model. The application team must still define data ownership, message meaning, authorization policy, retry safety, privacy boundaries, deployment configuration, and evidence that the whole path behaves correctly. Cloud architecture is therefore less about assembling the greatest number of services than about choosing a small set of clear responsibilities and making the transitions between them observable and dependable.
