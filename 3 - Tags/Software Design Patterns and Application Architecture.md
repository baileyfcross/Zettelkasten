# Software Design Patterns and Application Architecture

Parent topic: [[C Sharp and .NET Development]]

Software Design Patterns and Application Architecture is the chapter-level topic for reusable approaches to object construction, dependency management, data flow, persistence, and cloud operation. Full Notes should link to a focused child topic rather than directly to this chapter tag.

## Overview Chapter

A design pattern is useful when it names a recurring problem, identifies the forces that make the problem difficult, and offers a reusable arrangement of responsibilities. It is not a command to add classes or infrastructure wherever the pattern can be recognized. [[Software Design Principles]] provides the criteria for deciding whether a proposed structure helps. DRY asks whether one fact or behavior has been duplicated; KISS asks whether accidental complexity can be removed; YAGNI asks whether speculative features are being built before they are needed. A minimum viable product limits a delivery to the smallest useful set of behavior, while the SOLID principles ask how reasons for change, extensibility, substitutability, interface size, and dependency direction affect maintainability. These principles complement one another: abstraction can remove harmful duplication, but an abstraction introduced too early can violate simplicity and create work for a requirement that never arrives.

[[Object-Oriented Design Patterns]] translates those concerns into collaborations among objects. Creational patterns separate the decision to construct an object from the code that uses it. An abstract factory chooses a related family of products; a factory method delegates selection to a creator; a builder organizes a complex construction process; a prototype copies an existing object; and a singleton constrains instance count. Structural and behavioral patterns change how objects interact. A decorator wraps one object to add behavior without rewriting the wrapped implementation. A chain of responsibility passes a request among handlers, an observer publishes state changes to subscribers, a strategy selects one algorithm from several, and a command represents a request as an object. Their value lies in the particular seam they create for change, not in the number of pattern names an application contains.

The application must still create and connect its concrete objects. [[.NET Dependency Injection and Service Lifetimes]] moves that work to a composition boundary. Dependency inversion says high-level behavior should depend on stable abstractions rather than construction details; dependency injection is one way to supply the concrete implementations. The .NET service collection records mappings and lifetimes, and the service provider resolves them when needed. Transient instances are created on demand, scoped instances are shared within a defined boundary such as a web request, and singleton instances are shared across a provider. An implementation factory handles construction that needs explicit logic. These lifetimes do not make mutable code safe: a singleton used from several requests can still suffer races, and building a second service provider does not preserve the first provider's singleton identity.

[[Functional Programming in C Sharp]] offers another way to control complexity. A pure function returns the same result for the same inputs without changing external state, so it is easier to test and reason about. Referential transparency allows a call to be replaced by its value without altering a program's meaning. First-class and higher-order functions turn behavior into a value that can be passed, returned, or stored. C# delegates, lambdas, predicates, and LINQ make this style practical within an object-oriented language. A filtering function can receive its criterion as a function, which is a functional form of the strategy pattern. The design trade-off is to keep stateful I/O and mutation visible at the edges while making the central calculation as explicit as possible.

[[Reactive Programming in .NET]] extends composition from functions over fixed inputs to streams of values arriving over time. A stream can emit values, signal failure, or complete. Subscribers respond to notifications rather than repeatedly polling for changes. Streams can be merged, filtered, and mapped into other streams, allowing event-driven behavior to be described as transformations. The .NET `IObservable<T>` and `IObserver<T>` interfaces describe the provider-consumer contract, while Reactive Extensions supply operators for composing streams. A reactive system is a related but broader architectural idea: responsiveness, resilience, elasticity, and message-driven boundaries concern the behavior of the whole service, not simply the syntax of one observable pipeline.

At the persistence boundary, [[CQRS and Ledger Data Architecture]] separates recording a change from retrieving a view of current state. Online transaction processing favors efficient writes of operational changes; online analytical processing favors reading and aggregating historical information. A ledger-style table records each transaction as a new row, making corrections additional events instead of destructive edits. Summing the entire ledger on every request can become expensive, so a materialized or projected read model provides a faster view. Command Query Responsibility Segregation gives commands and queries distinct models, handlers, and potentially distinct data stores. That separation can support independent scaling and team ownership, but it also introduces synchronization delays: a successful write may not appear in the read model immediately. The pattern is therefore most useful when its read/write asymmetry and audit needs justify the consistency and operational cost.

[[Cloud Scalability and Resilience Patterns]] asks how an application behaves as demand or failures change. Vertical scaling gives one instance more resources; horizontal scaling adds instances, requiring a load distribution mechanism and careful treatment of session state. Auto-scaling changes capacity from measured conditions, but cannot repair a poor state model. Services built around business capabilities can be deployed independently when their contracts and data ownership are isolated. Event-driven architecture decouples a producer from consumers through events. Graceful degradation limits a failure's blast radius, and compensating transactions reverse the business effect of an earlier step when a later distributed step fails. A versioned service contract lets independent deployments evolve without silently breaking clients.

Finally, [[Cloud Messaging Caching and Operations Patterns]] turns those architectural goals into operational mechanisms. A queue buffers work so short spikes do not overwhelm a worker; publish-subscribe sends an event to each interested consumer; a priority queue gives selected work different treatment. Cache-aside places responsibility for misses and invalidation in application code, whereas a write-through cache coordinates writes through the cache service. Static content hosting moves media and scripts to a dedicated delivery network. Federated security delegates identity proof to a trusted provider, and telemetry centralizes observations from distributed services. Continuous integration and deployment turn code changes into repeatable builds, tests, and releases. Each pattern moves responsibility to a different boundary, so the crucial question is who now owns correctness when data changes, messages repeat, identities expire, or a deployment fails.

[[Domain-Driven Design]] applies that boundary question to business meaning itself. It develops a shared language with domain experts, uses EventStorming to expose behavior and uncertainty, and encodes business rules in entities, value objects, services, and aggregates. Commands and queries give external intent explicit shapes; repositories and event stores preserve aggregate state; projections produce read models; and bounded contexts keep incompatible meanings from being forced into one universal model. These techniques connect architecture to organizational structure because a model boundary is sustainable only when a team can understand and own it.

Together these topics move from local code to a distributed system without losing the same central concern: define a boundary that matches a real reason for change. Patterns are a vocabulary for evaluating those boundaries. They cannot replace clear requirements, tests, measurements, or operational evidence, but they can make a system easier to extend when the constraints they address are genuinely present.
