# Linux Kernel Programming

Parent topic: [[Computer Science]]

Linux Kernel Programming is the chapter-level topic for building and configuring Linux kernels, extending them with loadable modules, understanding task and memory internals, controlling CPU resources, and writing concurrency-safe kernel code. ## Overview Chapter

Linux kernel work joins software construction to the mechanisms that make an operating system run. The source tree is not merely compiled as one application: configuration chooses features, architecture support, security controls, and whether components are built into the image or as modules. [[Linux Kernel Build and Configuration]] follows this path from release and source-tree selection through Kconfig and Kbuild, compilation, module installation, initramfs generation, bootloader selection, and cross-compilation. These steps are connected by the configuration artifact: a build is meaningful only when the resulting image, modules, early userspace, and bootloader agree about the target machine and root filesystem.

Most practical kernel experiments do not require permanently changing the base image. [[Linux Kernel Module Development]] uses the loadable-module framework to add and remove code at runtime. A module declares metadata and lifecycle entry points, is built through the kernel's build system, and communicates through the kernel log rather than ordinary user-space libraries. Parameters make controlled behavior available at insertion or through sysfs, while module dependencies and stacking divide a larger feature across compilation units. Signing, licensing, lockdown, ABI instability, and coding-style checks make clear that loading privileged code is both a technical and a trust decision.

Once code enters the kernel, its execution context determines what it may safely do. [[Linux Process and Task Internals]] distinguishes process context from interrupt context and relates user threads, kernel threads, task structures, and per-thread stacks. Linux schedules threads rather than whole processes, so each live thread has a task descriptor even when several threads share one user address space. The `current` pointer identifies the executing task, task lists support system-wide iteration, and thread-group identifiers preserve the relationship between the main thread and its peers. These structures explain why the monolithic kernel can run system-call code on behalf of a user thread without delegating that work to a separate kernel process.

The addresses used by software are views constructed by the memory-management system. [[Linux Virtual Memory Internals]] follows a process from its user mappings across the user/kernel split into page tables, physical page frames, and the kernel's own virtual regions. Virtual memory areas describe homogeneous ranges, protection bits constrain access, and translation structures connect virtual addresses to RAM. Direct-mapped kernel memory supports fast access to ordinary page frames, while vmalloc and module regions occupy other portions of the kernel address space. ASLR and KASLR vary layouts to frustrate fixed-address attacks, and the sparse memory model keeps metadata for large or discontinuous physical address spaces.

Kernel code must also choose how memory is obtained and returned. [[Linux Kernel Memory Allocation]] begins with the buddy-based page allocator, the underlying engine that hands out physically contiguous power-of-two page blocks. The slab or SLUB layer builds reusable object-sized caches on those pages, making allocations smaller than a page fast while introducing size-class fragmentation that developers must measure. GFP flags describe context and reclaim behavior; `kmalloc`, `kzalloc`, `vmalloc`, and `kvmalloc` serve different contiguity and size needs. In the background, watermarks, `kswapd`, multigenerational LRU lists, and DAMON help observe or reclaim memory. Overcommit and demand paging postpone physical commitment, while the out-of-memory killer is a last-resort policy when reclaim cannot satisfy demand.

CPU time is another managed resource. [[Linux CPU Scheduling and Control Groups]] describes task states, scheduling policies, per-CPU runqueues, modular scheduling classes, fair scheduling through virtual runtime, affinity masks, and the context switch that installs the next task's memory and register state. Control groups add hierarchy and accounting above individual tasks, allowing a controller to distribute CPU bandwidth or constrain memory and other resources for a workload. Systemd maps services, scopes, and slices onto that hierarchy, and containers rely on the same control and namespace foundations. Real-time Linux changes preemption and locking behavior to reduce worst-case latency, emphasizing predictable deadlines rather than merely a low average response time.

Concurrency turns these subsystems into shared-state problems. [[Linux Kernel Locking]] starts by identifying critical sections: code that can execute concurrently and accesses shared writable data. A mutex sleeps while waiting and therefore belongs in process context; a spinlock is suitable for short non-blocking sections and for atomic or interrupt contexts. Interrupt-aware variants additionally control local interrupt or bottom-half execution. Consistent lock ordering prevents circular waits, priority inheritance addresses priority inversion, and specialized reader-writer or sequence locks serve particular access patterns. Lockdep and lock statistics turn the intended locking design into evidence by detecting dependency cycles and exposing contention.

Not every scalable design should serialize readers. [[Linux Kernel Lock-Free Synchronization]] covers atomic integer and bit operations, reference counts, per-CPU variables, cache coherence, false sharing, memory ordering, and Read-Copy-Update. Per-CPU state removes a shared write point by giving each processor a local instance. RCU lets readers traverse an old version while a writer prepares and publishes a replacement, then waits through a grace period before reclaiming the old object. This shifts work away from read-heavy paths but imposes strict rules about read-side critical sections and object lifetime. Memory barriers and marked accesses control when loads and stores become observable across CPUs or devices; they complement, rather than replace, a correct synchronization design.

Together these topics form a dependency chain. Configuration determines what mechanisms exist; modules provide a controlled place to exercise them; task and address-space models explain execution; allocators and the scheduler manage memory and CPU resources; and synchronization preserves correctness as cores, interrupts, and devices act concurrently. Kernel programming is therefore less about calling privileged APIs than about respecting context, ownership, lifetime, ordering, and the contracts connecting every layer.
