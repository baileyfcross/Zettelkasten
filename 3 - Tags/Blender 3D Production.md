# Blender 3D Production

Parent topic: [[Computer Science]]

Blender 3D Production is the chapter-level topic for creating, animating, simulating, rendering, and compositing visual work in Blender. Full Notes should link to one of the focused child topics rather than directly to this chapter tag.

## Overview Chapter

Blender organizes 3D production as a connected set of representations and workspaces. The same scene data can be modeled, shaded, animated, simulated, rendered, edited, and composited without leaving the application. That breadth is useful only when the artist understands how Blender divides the work: windows contain configurable areas, areas host editors, and editors expose different views of shared scene data. [[Blender Interface and Workflow]] establishes this structure through editor types, Properties contexts, workspace presets, preferences, keymaps, search, and Quick Favorites. The interface is therefore not a collection of unrelated screens but a configurable environment whose layout can follow the current task.

Working in three dimensions begins with the view and the object. [[Blender 3D Viewport and Object Operations]] explains how orbiting, panning, zooming, projection modes, standard views, selection, the 3D cursor, and Quad View make a spatial scene legible on a flat display. Objects are placed with translation, rotation, and scale, expressed through coordinate orientations, gizmos, hotkeys, or exact numeric input. Parent-child relationships organize inherited motion, while collections group scene elements without merging their underlying data.

The scene also contains several kinds of data-bearing containers, organized in [[Blender Scene Object Types]]. Meshes store polygonal surfaces, curves and surface objects describe mathematically controlled forms, metaballs blend implicit volumes, and text remains editable through curve geometry. Armatures supply skeletal controls, lattices deform other objects through a cage, and empties provide transformable reference points without renderable geometry. Grease Pencil, lights, cameras, speakers, and probes extend the same object system to drawing, illumination, viewing, sound, and real-time capture.

[[Blender Mesh Modeling and Modifiers]] moves from whole objects to their components. Object mode controls an object as a unit; Edit mode exposes vertices, edges, and faces. Selection of connected components, extrusion, separation, inset cuts, knife cuts, bevels, loops, and rings build and refine topology. Modifiers add a nondestructive layer above the base mesh. Their order matters because each modifier receives the result of the one above it; Mirror, Subdivision Surface, and Array show how symmetry, smoothness, and repetition can remain adjustable instead of being committed immediately.

Once the broad mesh workflow is established, [[Blender Mesh Shaping Tools]] distinguishes specialized operations by the relationship they preserve. Smooth and randomize alter vertex positions, slide tools move components along existing topology, shrink/flatten and push/pull act relative to normals, and shear or To Sphere imposes a more specific spatial transformation. Spin and spin-duplicate create rotational repetitions, proportional editing spreads a transform through a falloff, and the post-operation panel exposes parameters that can be revised immediately after a tool runs.

Not every form is best produced by polygon editing. [[Blender Sculpting and Geometry Objects]] treats a dense mesh as virtual clay, using reference images, specialized brushes, adjustable radius and strength, brush textures, multiresolution levels, and dynamic topology. A sculpt can later be retopologized into a cleaner mesh suited to animation or rendering. Curves and surfaces describe precise forms mathematically, metaballs merge like controllable droplets, and text objects bring editable typography into three-dimensional scenes.

Surface appearance is constructed in [[Blender Materials and Textures]]. Material slots assign distinct surfaces to components, while vertex colors interpolate color across mesh vertices. Node materials connect shaders to a Material Output, with the Principled BSDF gathering many physically based controls into one shader and Mix Shader combining surface behaviors. Procedural and image textures require coordinates that specify where their data belongs. UV unwrapping flattens a mesh through deliberate seams, after which the artist can paint directly on the model and save both the painted image and UV layout for external work.

Two focused topics expand that handoff from surface geometry to pixels. [[Blender UV Mapping and UDIM]] compares live and automatic unwrapping, projection methods for different forms, seam and island control, UV selection and sculpting, and tiled UDIM layouts for distributing resolution. [[Blender Texture Painting Workflow]] then connects those coordinates to direct painting in the 3D Viewport or Image Editor. Brush textures, masks, stroke methods, falloff, symmetry, slots, canvas images, bleed, occlusion, palettes, and image saving determine whether painted detail remains controlled and portable.

Color decisions operate above any single tool. [[Color Design for Game Environments]] uses the color wheel, hue, saturation, value, additive and subtractive systems, cultural meaning, and families of color harmony to shape mood and guide attention. Monochromatic and analogous palettes emphasize cohesion, complementary and split-complementary schemes introduce controlled contrast, and triadic or tetradic structures distribute several hues. Environment color therefore supports navigation and atmosphere while remaining sensitive to context and color-vision accessibility.

Appearance also depends on illumination and output. [[Blender Lighting and Rendering]] begins with key, fill, and back lights, then extends to Blender's light types, the World environment, ambient occlusion, and Eevee light probes. Eevee emphasizes rapid physically based results, Cycles follows a more complete light-transport approach, and Workbench serves fast previews. A render converts the active camera's scene into an image; output properties choose resolution and file format, while animation is safer as an image sequence that can later be assembled or composited. Exporting instead translates scene data for another program or production pipeline.

Movement is organized through [[Blender Keyframe Animation and Rigging]]. Keyframes record important states and f-curves interpolate between them. Keying sets coordinate many properties, the Graph Editor shapes rates of change, and the Dope Sheet exposes overall timing. Constraints relate one object's motion to another. Shape keys store modeled deformations, hooks provide looser control over selected points, and armatures provide a structured skeleton whose bones influence a weighted mesh. Forward kinematics propagates rotations down a chain; inverse kinematics solves the chain from a desired endpoint. Actions and the Nonlinear Animation editor let completed motions be reused, mixed, and looped.

[[Blender Simulation and Grease Pencil]] covers two ways Blender can generate motion beyond ordinary object keys. Physics systems calculate particles, forces, collisions, hair, soft bodies, rigid bodies, cloth, fluids, smoke, and fire from rules and initial conditions. Caching stabilizes playback and avoids recalculating every frame. Grease Pencil takes another route: its curve-based strokes exist in 3D space, receive materials, occupy ordered layers, accept modifiers, and can be animated either by repeated drawing or by a rig. It connects a hand-drawn visual language to the same cameras, lighting, and compositing tools used by 3D scenes.

Once shots exist, [[Blender Video Editing and Compositing]] assembles and refines them. The Video Sequencer is a nonlinear editor whose strips can be moved, trimmed, layered, blended, and joined by effects or transitions. Editing primarily arranges shots over time; compositing primarily stacks and processes visual elements within a shot. The Compositor represents that processing as a left-to-right node network. View layers and render passes isolate components such as depth, shadows, motion, or materials; Cryptomatte produces robust masks; node groups package reusable operations; and OpenEXR MultiLayer can preserve passes for later work.

Finally, [[Blender Motion Tracking]] connects recorded footage to a reconstructed 3D camera. Reliable work begins during capture: camera and lens data, stable light, sharp progressive frames, and measured scene dimensions make features easier to track. Markers follow distinctive image regions over time, automatic feature detection proposes candidates, and the solver estimates the camera's changing position and orientation. A floor or wall defined from suitable tracks anchors that solution to the scene. Blender can then create reference geometry, use the footage as a camera background, and build a starter composite so rendered objects share perspective and motion with the recorded shot.

Python adds a programmable layer across this production system. [[Blender Python Scripting Environment]] begins with the development loop inside the application: actions performed through the interface reveal operator calls in the command log, those calls can be simplified and tested in the interactive console, and successful experiments can become scripts in the Text Editor. The editors have separate local Python scopes but share the same Blender data, allowing a model to be changed through one interface and inspected through another. Configurable workspaces place code, scene, console, and diagnostic output together, while a system terminal exposes warnings and tracebacks. This continuity lets a repeated user action grow gradually into automation.

[[Blender Python Data and Operations]] explains the structure behind that automation. The `bpy` module separates operators, current context, persistent datablocks, and application services. Operators express actions and usually depend on mode, selection, and the active object; direct datablock access names a particular object or resource and assigns its properties explicitly. Selection, activation, and specification are therefore different relationships even when they temporarily identify the same object. Scripts become reliable by declaring which relationship they need and by choosing between relative operator-driven transformations and direct declarative updates.

Whole-object manipulation is not enough for procedural modeling, so [[Procedural Mesh Editing with bmesh]] descends into editable topology. A BMesh exposes vertices, edges, and faces whose selection state can drive familiar Edit Mode transforms, extrusion, and subdivision. Lookup tables must be refreshed after topology changes, and temporary BMesh references should not be treated as permanent data. More importantly, numeric component indices are reproducible only under controlled versions and operation histories. Selecting components by location or another geometric characteristic produces more portable algorithms. Global and local coordinates make that characteristic explicit, while repeated rule-based selections and extrusions turn simple primitives into growing forms.

Those forms eventually have to be stored or exchanged. [[Portable 3D Model Data]] reduces a surface to vertices, indexed faces, normals, and optional texture coordinates, then compares the choices made by common formats. OBJ and its material companion can reuse indexed geometry and carry UVs and normals; STL repeats the vertices of triangular facets; PLY declares polygonal data through a header and element records. Blender's native file preserves a much wider application state, while interchange formats deliberately restrict themselves to a portable subset. Indexed representation, coplanar face reduction, consistent normal orientation, and the removal of overlapping surfaces all affect whether a model remains compact and renders correctly after transfer.

Transfer becomes a production pipeline in [[Open-Source Game Engine Asset Pipelines]]. Godot watches its project folder, imports formats such as glTF, and turns imported scenes into reusable instances inside a node hierarchy. Stride combines a modular asset toolchain with C# scripting, physically based rendering, and customizable shaders. Armory3D keeps more of the process inside Blender, compiling Cycles-style material nodes for real-time rendering and exporting through its cross-platform stack. Each route still requires the artist to verify scale, orientation, materials, hierarchy, and animation after import.

The constraints behind those exports begin much earlier in [[Low-Poly Game Environment Art]]. Polygon complexity is relative to target hardware, game type, camera distance, and the role of an asset in the scene. Environment art establishes architecture, mood, and visual identity, while level design emphasizes playable challenges and progression. Retopology, baked surface detail, texture filtering, mipmaps, and distance-based levels of detail let a project preserve important visual information without assigning close-up complexity to every background object.

Reusable tools need an application-facing structure as well as a modeling algorithm. [[Blender Add-On Architecture]] organizes a tool around metadata, operator classes, panel classes, typed properties, and a reversible registration lifecycle. Operators expose executable behavior, panels place controls in a Blender area, and scene or object properties preserve values that the interface can display and edit. Poll methods restrict tools to contexts where they are meaningful, while enumerations turn constrained choices into menus. Although individual registration helpers differ by Blender version, the durable design rule is that every installed class, property, and handler must have a clear activation and cleanup path before the package is distributed.

Some tools need to communicate without altering the model. [[Blender Viewport Drawing API]] treats names, vertex indices, lines, and measurements as transient overlays regenerated whenever the viewport draws. Application handlers respond to broader events such as frame changes or file loading, while viewport draw handlers attach functions to the visual update cycle. In the historical API described here, `bgl` supplies OpenGL-style lines and state changes and `blf` supplies positioned text. Three-dimensional scene points are projected into two-dimensional canvas coordinates, graphics state is restored after each callback, and an operator retains the handler reference so a button or add-on shutdown can remove the overlay cleanly.

As an add-on grows, its development environment should resemble its deployed environment. [[Blender Add-On Development Workflow]] moves code from the internal Text Editor into Blender's add-on filesystem, where an external editor can manage a single script, flat package, or multilevel Python module. Reloading recompiles changed files and exercises registration cleanup; import management ensures sibling modules refresh instead of remaining cached. External model data creates another architectural decision. Stable detailed assets are usually clearer as interchange files, strongly parameterized forms favor algorithmic manipulation of primitives, and hardcoded mesh arrays are best reserved for cases where the data is genuinely inseparable from the procedure. Rows, columns, boxes, labels, separators, and icons then shape those capabilities into a usable panel.

The programmable pipeline reaches final appearance through [[Automated Blender Texturing and Rendering]]. Texture data has both a source and an influence: an image or procedure supplies values, while material settings determine whether they affect color, reflection, transparency, or rendered surface detail. Materials group coordinated textures before they are assigned to objects. UV data belongs to face loops, allowing one spatial vertex to use different image coordinates across a seam. Once unused test datablocks are cleaned away, the scene's aggregate bounds can guide light placement and camera aim. Field of view, aspect ratio, and a safety margin determine camera distance, after which a full still render or a faster viewport snapshot can be written automatically.

Developing the application itself begins beneath those user-facing systems. [[Blender Core Source Architecture]] treats the repository as an executable hierarchy of modules rather than a flat collection of files. Core code resides primarily under `source/`, internally maintained support libraries occupy `intern/`, and public headers separate a module's API from implementation files in its own `intern` directory. CMake build descriptions repeat through the tree so modules and optional capabilities can be assembled for different platforms. At runtime, `main()` initializes global state and the window manager before entering a loop that gathers events, executes handlers, processes notifiers, and draws. This loop updates model state before the view, making the application's ordering as important as its directory layout.

Persistent state follows the path described by [[Blender DNA and File Loading]]. A blend file is largely a binary serialization of C structures, but its header and DNA1 block make it self-describing by recording version, pointer size, byte order, names, types, lengths, and structure layouts. Blender compares that stored SDNA with the current version, applies rename maps and structural conversion, reconstructs direct data, and links datablocks into the central `Main` database. The factory startup scene follows the same route even though its bytes have been converted into a C array and embedded in the executable. After loading, context accessors install the rebuilt `Main` so editors and operators see one coherent application state.

The border between that core and the host operating system is [[Blender GHOST Windowing]]. GHOST presents abstract system, window, context, event, and timer interfaces, then selects concrete Win32, X11, or Cocoa classes behind them. Because GHOST is C++ and much of Blender is C, opaque handles and adapter functions preserve the language boundary while retaining polymorphic dispatch. Window creation obtains a native window and OpenGL context, and event consumers carry low-level system input back to Blender. Its process-and-dispatch calls form the first event stage, leaving Blender's own window manager in control of the main loop instead of surrendering that loop to a framework.

Two lower modules supply much of the common behavior used by the rest of the program. [[Blender Library and Kernel Internals]] distinguishes `blenlib`, a broad collection of containers, math, hashing, paths, memory, geometry, threading, and other utilities, from `blenkernel`, whose functions manipulate Blender-specific data. Their `BLI_` and `BKE_` APIs express that difference, while the `CTX_` API gives controlled access to current application context. DNA headers often pair with kernel headers that create, copy, evaluate, localize, and free the corresponding records. Google Test, CTest integration, Blender-specific assertion helpers, Doxygen output, and debug traces provide several partial but complementary ways to understand and verify these interfaces.

The application exposes another boundary through [[Blender Embedded Python Internals]]. Blender links CPython, registers built-in modules before interpreter initialization, and offers BPY entry points for executing files, Text datablocks, and expressions. Extension modules describe functions with module and method tables, while extension classes use `PyTypeObject` records and a common object header to approximate inheritance in C. The `mathutils.Vector` implementation shows the full route: construction allocates or wraps float storage, get-set records control attributes, and a method table dispatches Python calls to C functions that reuse blenlib math. Compiled Text datablocks can retain bytecode, and access from concurrent native work must respect CPython's global interpreter lock.

Python, operators, and the interface converge through [[Blender RNA Data Architecture]]. RNA describes DNA structures with identifiers, property types, defaults, ranges, accessors, update functions, and UI text. The `makesrna` build first runs a non-runtime generator from handwritten `RNA_def_*` declarations, then compiles the emitted records and accessors into Blender. `StructRNA` and its property container describe a type, `PropertyRNA` derivatives describe individual values, and `PointerRNA` pairs those descriptions with actual data. Operator settings travel through these pointers, and Python-facing objects embed them so attribute reads and writes reach the same Data API rather than bypassing the persistent model.

The visual application is organized by [[Blender Editor Structure]]. A native GHOST window is wrapped by a Blender window, which selects a saved screen divided into rectangular areas. Each area joins persistent `SpaceLink`-derived editor data to a runtime `SpaceType` containing callbacks, supported regions, and operator registration. Regions repeat that data-and-type pairing at a smaller scale through `ARegion` and `ARegionType`. Startup collects all space types in a global registry; later drawing and event code can match saved numeric identifiers to the current executable's behavior. This design lets an area switch from one editor to another while screens, regions, and handlers remain explicit parts of the application state.

Interaction moves through [[Blender Operator and Event System]]. An operator type stores identity, RNA properties, and callbacks; an operator instance carries the property values and state for one invocation. Non-modal operations commonly poll the context and execute once, while modal operations retain state across repeated events. Registered types live in a hash keyed by module- or editor-prefixed names. GHOST events become Blender event records in a window queue, after which the dispatcher locates the active area and region, updates context, and walks its handlers. The result is a layered route from physical input to a context-valid operation rather than a direct call from the operating system to model code.

[[Blender Editor Construction]] brings these layers together by defining a new editor in C. Registration creates a space type and header and window region types; the editor constructor allocates its persistent space data and region instances. The main loop draws marked regions into offscreen buffers before presenting them, and region dispatch calls the custom draw function registered in the type record. View2D supplies drawing bounds, while Blender's GPU wrapper clears buffers and emits primitives without direct editor-level OpenGL calls. Header buttons belong to UI blocks and point to registered operators whose callbacks update editor data and request redraw. Build files, public declarations, DNA, context access, and RNA definitions must all acknowledge the new editor if it is to compile, persist, and remain available to scripted UI.

Across the workflow, Blender repeatedly favors editable relationships over irreversible results. Workspaces expose common data for different tasks; modifiers preserve the base mesh; nodes preserve the steps of a material or composite; rigs separate controls from deformation; and passes preserve parts of a render. Production becomes a sequence of linked decisions in which modeling affects UVs, materials respond to light, animation changes simulation, the camera defines rendering, and editing and compositing determine how the final images are experienced.
