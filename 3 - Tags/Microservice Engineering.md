# Microservice Engineering

Microservice Engineering is the chapter-level topic for deciding when independently deployable services are justified and for designing, delivering, securing, and operating them as one distributed system. Full Notes should link to a focused child topic rather than directly to this chapter tag.

## Overview Chapter

Microservices exchange one kind of simplicity for another. A monolith keeps deployment, local calls, and transaction boundaries together, but it can make independent change and selective scaling difficult as the system and organization grow. A microservice architecture separates business capabilities into independently operated services, which gives each service a clearer change boundary and lets teams deploy or scale it without rebuilding the whole application. That benefit is conditional. Every new process boundary introduces a network interaction, a contract to evolve, operational state to observe, and data that may no longer participate in one local transaction. The central engineering question is therefore not how small a service can be, but whether a proposed boundary creates enough independent value to justify the distributed-system cost.

[[Microservice Architecture Adoption]] develops that decision. Service autonomy combines focused responsibility with independent execution, deployment, and lifecycle ownership. A service can adopt a suitable technology and scale according to its own workload, while failures can be contained rather than automatically bringing down the whole application. Yet autonomy also multiplies deployment pipelines, runtime configurations, diagnostic surfaces, and cross-service failure modes. A thoughtful migration begins with a well-understood domain and extracts services where changing, scaling, or owning a capability separately solves an observed problem. Premature decomposition produces coordination overhead without removing conceptual coupling. Continuous delivery and automation are consequently architectural requirements: independent deployment is meaningful only when builds, tests, configuration, rollout, and recovery are repeatable.

The boundaries themselves are the subject of [[Microservice Boundaries and Data]]. Domain-driven design uses business capabilities, bounded contexts, and a shared language to identify places where a model can remain internally consistent. A service should own the behavior and data that implement its capability, exposing an explicit interface rather than allowing other services to reach into its database. Database-per-service and polyglot persistence reinforce autonomy, but they also replace convenient cross-table transactions with duplicated data, events, and eventual consistency. Over-segmentation scatters one capability across many services and makes ordinary work network-bound; under-segmentation leaves unrelated reasons for change together. A defensible boundary balances cohesive business meaning, team ownership, data authority, and the cost of coordinating operations that cross it.

Once boundaries exist, [[Microservice Communication and Resilience]] governs how they collaborate. Synchronous calls provide an immediate response and straightforward request flow, but make the caller wait and can propagate latency or failure through a call chain. Asynchronous messaging separates producer availability from consumer availability and can buffer spikes, though it requires explicit handling of delivery, ordering, retries, idempotency, and event evolution. Service discovery maps logical service identities to changing instances; an API gateway can route, aggregate, authenticate, cache, and throttle external requests; and a backend for frontend can tailor that gateway role to a client type. Sidecars can supply common operational behavior beside application containers. Resilience patterns such as circuit breakers, retries, timeouts, bulkheads, and fallbacks limit how dependency failure spreads, but each needs thresholds and behavior matched to the service contract.

Independent services also need independent evidence of correctness. [[Microservice Testing Deployment and Scaling]] connects isolated unit tests to integration tests, end-to-end flows, and consumer-driven contract tests. Unit tests give fast feedback about local behavior; integration tests exercise framework and dependency boundaries; end-to-end tests check a small number of critical workflows across services. Contract tests verify that a provider and its consumers agree on request and response shapes without requiring every service to be deployed together. Containers package a service and its dependencies, while Kubernetes Deployments, Services, probes, and autoscaling manage replicas. Horizontal scaling adds instances instead of enlarging one instance, so statelessness, load distribution, and downstream capacity matter. Liveness and readiness answer different questions: whether a container should be restarted and whether a pod should receive traffic.

Distribution makes operational evidence and trust boundaries first-class concerns, addressed by [[Microservice Security and Observability]]. Tokens can carry client identity and authorization context, while TLS and mutual TLS protect service-to-service communication and authenticate endpoints. Network segmentation, gateway controls, rate limits, key rotation, and least-privilege authorization reduce the blast radius of a compromised component. Centralized, structured logs need service, environment, request, and correlation context so one transaction can be reconstructed across ephemeral instances. Distributed traces connect spans across calls; metrics expose rates, errors, latency, saturation, and health; dashboards interpret those signals; and alert rules turn selected conditions into action. Observability must be designed with the architecture because missing context, sensitive data in logs, unbounded labels, or noisy alerts can make abundant telemetry less useful rather than more useful.

[[Helidon Microservices Framework]] shows how one Java runtime packages these architectural concerns into two programming models. Helidon SE uses explicit functional builders for servers, clients, configuration, data, and security, while Helidon MP uses MicroProfile and selected Jakarta standards with annotations and dependency injection. Both run as standalone services on Helidon's virtual-thread server. Configured routes, database statements, security providers, metrics, fault-tolerance policies, and health endpoints make service boundaries and operational behavior concrete without requiring an external application server.

These topics form one feedback loop. Business boundaries determine data ownership and communication paths. Communication paths determine failure modes, security controls, and the tests needed to protect contracts. Deployment and scaling change which instances exist, making discovery, health checks, and telemetry necessary. Production evidence then shows whether a boundary is too chatty, a dependency too fragile, or an autoscaling rule too slow. Microservice engineering succeeds when teams use that evidence to revise boundaries and operational practices, not when they maximize the number of services.
