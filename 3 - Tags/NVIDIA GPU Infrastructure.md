# NVIDIA GPU Infrastructure

NVIDIA GPU Infrastructure is the chapter-level topic for the hardware, software, data paths, sharing mechanisms, inference services, and operating practices that turn NVIDIA accelerators into production AI platforms. ## Overview Chapter

A GPU platform succeeds only when computation, data movement, software compatibility, resource allocation, and operations reinforce one another. Installing an accelerator does not by itself create useful capacity. A model must expose suitable parallel work, its working state must fit in device memory, data must arrive quickly enough, and the host software must translate framework operations into instructions the hardware can execute. Production adds another set of constraints: several tenants may need to share expensive devices, model versions must be delivered reproducibly, inference must meet latency and throughput targets, and operators need evidence that distinguishes an application problem from a driver, container, scheduler, network, or hardware problem.

[[CUDA and NVIDIA GPU Architecture]] explains the execution foundation. CUDA represents a kernel launch as a grid of thread blocks; blocks are assigned to streaming multiprocessors, where threads execute in warps. Keeping several warps ready lets a scheduler issue other work while one warp waits on data, a form of latency hiding rather than elimination. Tensor Cores accelerate supported matrix multiply-accumulate operations, while cuBLAS and cuDNN provide optimized linear-algebra and neural-network primitives above CUDA. Mixed precision trades representation range and accuracy for memory efficiency and throughput, so lower precision must be validated rather than assumed safe. CUDA Graphs reduce repeated launch setup for stable sequences of small operations. Nsight Systems and Nsight Compute then connect performance symptoms to, respectively, an application-wide timeline and individual-kernel behavior.

Hardware capability must still be matched to a real workload. [[NVIDIA Data Center GPU Selection]] begins with training versus inference, then examines model state, device-memory capacity, memory bandwidth, compute throughput, numerical formats, graphics needs, and interconnect topology. Training often stores weights, gradients, optimizer state, activations, and batch data, while inference emphasizes serving state, concurrency, batching, and response objectives. NVLink and NVSwitch reduce communication penalties for supported multi-GPU systems, but they do not remove the need for distributed software or topology-aware placement. Product families such as A100, H100, L40S, and B200 embody different balances of maturity, large-model throughput, graphics capability, memory, and low-precision support. Selection therefore follows measured constraints and the exact server configuration rather than a simple newest-is-best ranking.

Once deployed, the devices become a shared fleet. [[NVIDIA GPU Sharing and Fleet Management]] connects allocation, monitoring, and scheduling. Multi-Instance GPU divides supported hardware into predefined compute-and-memory profiles with stronger resource and fault isolation than software-only sharing. Packing profiles efficiently requires understanding the demand distribution rather than merely maximizing the number of instances. DCGM gathers fleet telemetry, diagnostics, health events, and policy signals; its host engine supplies data to command-line, API, and exporter clients. Kubernetes exposes full GPUs or MIG resources declaratively to pods, while Slurm queues research and batch jobs against requested resources. Capacity decisions should combine utilization, memory pressure, temperature, power, errors, service latency, and workload context instead of treating one percentage as a verdict.

Accelerators also depend on the path that feeds them. [[Accelerated GPU Storage and Networking]] follows data from storage or a remote peer toward GPU memory. A traditional CPU-centered route can introduce host-memory staging, kernel transitions, interrupts, and repeated copies. GPUDirect Storage and GPUDirect RDMA shorten supported paths, while RDMA reduces remote CPU and kernel involvement through registered memory regions and capable adapters. Ethernet offers broad compatibility and familiar operations; InfiniBand provides a purpose-built low-latency fabric with native RDMA; hybrid designs assign management, service, storage, and tightly synchronized training traffic to appropriate networks. None of these labels guarantees performance. The effective path depends on drivers, filesystems, adapters, topology, congestion control, and measurement that confirms the optimized route is actually active.

[[GPU Virtualization and DPU Offload]] separates two other infrastructure boundaries. NVIDIA vGPU presents assigned accelerator resources inside virtual machines through a hypervisor, host manager, guest driver, profiles, scheduling policy, licensing, and telemetry. MIG instead creates hardware partitions and can, on supported platforms, sit underneath a vGPU. The right first question is therefore whether the service boundary is a virtual machine or a hardware-isolated slice. A data processing unit addresses a different problem: BlueField places Arm cores, memory, high-speed interfaces, and accelerators close to the network and storage data plane. DOCA makes that layer programmable for packet processing, storage, security, encryption, telemetry, and tenant isolation. CPU, GPU, and DPU remain complementary processors for control logic, parallel model computation, and infrastructure data movement.

A trained model needs its own production path. [[NVIDIA AI Inference Stack]] distinguishes portability, optimization, and serving. ONNX provides a framework-neutral model representation, TensorRT converts supported models into engines optimized for a target NVIDIA environment, and Triton supplies a multi-framework inference service. Triton can combine compatible requests through dynamic batching, run multiple models concurrently, compose ensembles, organize versions in a model repository, and expose serving metrics. These mechanisms solve different problems: batching amortizes overhead, concurrency shares capacity, ensembles compose processing stages, and model control modes determine when repository changes become active. The complete path validates every transition from training output through ONNX export, TensorRT optimization, repository packaging, Triton serving, and production observation.

Finally, [[NVIDIA GPU Platform Operations]] turns components into a maintainable service. NGC supplies curated containers, models, resources, and Helm charts, but an organization still needs pinned identities, scanning, testing, private distribution, approval, and rollback. The NVIDIA Container Toolkit exposes host devices and driver capabilities to containers; the device plugin advertises schedulable resources; the GPU Operator reconciles node software; and DCGM Exporter connects device signals to cluster monitoring. Safe operation records healthy baselines, places tightly coupled jobs on suitable interconnects, validates releases with real GPU work, and troubleshoots from broad configuration evidence toward deeper profiling. NVIDIA-SMI offers a quick state check, DCGM supplies fleet history, Nsight Systems locates application-wide delay, and Nsight Compute explains a slow kernel.

Together, these layers form one dependency chain. Workload characteristics choose the hardware and sharing model; architecture determines how computation executes; storage and networks determine whether devices remain supplied; virtualization and DPUs establish tenant and data-plane boundaries; inference tools turn artifacts into services; and platform operations preserve compatibility and evidence over time. Reliable GPU infrastructure comes from locating each requirement at the correct layer and validating the complete path rather than optimizing one component in isolation.
