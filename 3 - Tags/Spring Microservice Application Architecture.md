# Spring Microservice Application Architecture

Parent topic: [[Microservice Engineering]]

Spring Microservice Application Architecture is the chapter-level topic for assembling, testing, securing, observing, and operating Spring Boot applications and Spring Cloud services. Full Notes should link to a focused child topic rather than directly to this chapter tag.

## Overview Chapter

Spring Boot turns the Spring Framework's component model into an independently runnable application platform. Its convenience comes from a sequence of inspectable decisions rather than hidden behavior: dependencies identify capabilities, conditions decide which configuration applies, component scanning finds application beans, and explicit user definitions override defaults. The resulting application can expose synchronous or reactive interfaces, use several data-access styles, publish messages, integrate identity, emit telemetry, and participate in a distributed service architecture. The framework is most effective when these concerns remain separated into clear boundaries instead of accumulating in one controller or configuration class.

[[Spring Boot Configuration and Extensibility]] covers the application's composition boundary. Spring Initializr establishes a reproducible project and curated starter set. The bootstrap annotation combines Boot configuration, component scanning, and auto-configuration, while conditional configuration examines the classpath, bean registry, and properties before contributing infrastructure. External properties and profiles let the same artifact run in different environments without source changes, and type-safe configuration binding groups related values into validated objects. Scheduling and logging are further container services rather than code that every feature must construct independently. The same mechanisms support extension: a custom starter separates dependency aggregation from auto-configuration, registers its configuration through Boot metadata, backs away when the user supplies a replacement bean, and can expose an explicit enable annotation when opt-in behavior is preferable.

Those configured components meet clients through [[Spring Web and Service Interfaces]]. In Spring MVC, the DispatcherServlet coordinates handler selection, argument binding, controller execution, message conversion, and the response. A REST controller should translate HTTP concerns while delegating business behavior to an application service. Versioned routes can preserve an older contract while a stricter representation and validation policy is introduced. Controller advice centralizes safe Problem Details responses, and content negotiation selects a converter from the client's declared media types. Outbound HTTP interfaces reverse the direction: an annotated Java contract can be backed by RestClient without hand-writing each exchange. GraphQL adds schema-directed field selection and batch mapping for relationship loads, while `ArgumentValue` distinguishes an omitted mutation input from an explicit null. gRPC uses a Protocol Buffer contract and generated stubs for strongly typed HTTP/2 communication. HAL and Spring HATEOAS remain useful when a REST representation needs discoverable transitions.

[[Spring Data Access and Persistence]] keeps storage choices behind repository and transaction boundaries. JdbcTemplate handles connection lifecycle, statement execution, row iteration, resource cleanup, and exception translation; JdbcClient presents the same foundation through a fluent interface, named parameters, and direct record mapping. Spring Data can generate a repository implementation and derive queries from method names. Spring Data JDBC favors small aggregates, eager loading, and predictable saves without a persistence context, whereas JPA supplies richer entity relationships, dirty checking, and pagination for more complex object graphs. R2DBC preserves a nonblocking path to relational storage for WebFlux applications. MongoDB repositories, Redis session storage, and Neo4j's graph client show that one application can use different stores for documents, transient state, and relationship traversal. Declarative transactions make a service operation atomic, while TransactionTemplate narrows a transaction programmatically when the annotation boundary is too broad.

Fast feedback depends on [[Spring Application Testing]]. A unit test can exercise one object without the container; a test slice loads only the framework layer needed for a controller, JSON mapper, HTTP client, or reactive handler; and `@SpringBootTest` loads a full application context when the behavior crosses those boundaries. RestTestClient offers one fluent HTTP assertion model for a controller bound in memory or a real server on a random port. Bean-override annotations replace or spy on selected collaborators without rebuilding the production graph. Recorded application events make internal publication observable to a test. Testcontainers service connections derive runtime connection properties from a real disposable dependency, reducing false confidence from an unlike embedded substitute. Context pausing and modular test starters control the threads, infrastructure, and memory retained by a large suite.

Authentication and authorization belong to [[Spring Security and Identity]]. A SecurityFilterChain applies request matching, authentication, exploit protection, and authorization before a controller runs. A catch-all authenticated rule protects new routes that were not explicitly considered, while method security enforces role, authority, or instance-level rules at the service operation itself. Custom meta-annotations give repeated authorization expressions a stable name. UserDetailsService adapts an application's identity store to Spring Security, and DelegatingPasswordEncoder allows new password hashes to use a strong scheme while older formats remain recognizable during migration. One-time-token login supports passwordless links, TOTP adds a second factor, and a reactive filter chain carries identity without blocking the WebFlux event loop. SSL bundles centralize key and trust material. Mutual TLS authenticates workload certificates at the connection boundary, while scoped tokens still authorize the particular action.

Within and between applications, [[Spring Messaging and Integration]] provides several levels of decoupling. Application events separate beans in one context, and a transactional event listener can wait for commit before acting on a change. JMS gives a standard queue/topic API, RabbitMQ adds exchange-and-binding routing and replayable streams, Kafka supplies a partitioned retained log, and Pulsar combines queuing and streaming through subscriptions. RSocket maintains a multiplexed Reactive Streams connection with request-response, fire-and-forget, stream, and channel interactions. WebSocket with STOMP gives browser clients named destinations over a full-duplex connection. Spring Integration composes filters, transformers, routers, splitters, aggregators, and endpoint adapters as an explicit flow. Choosing among them depends on whether the boundary is in-process or remote, destructive or replayable, request-oriented or streaming, and whether ordering, backpressure, or transaction coupling is required.

Finally, [[Spring Cloud Operations and Native Runtime]] addresses the application as an operated member of a wider system. Config Server retrieves environment properties from a managed backend, Consul supplies changing service locations and health, client-side load balancing selects an instance, and Gateway provides a discovery-aware edge route for common policy. Spring Cloud Stream binds functions to a broker, Contract verifies consumer expectations against provider behavior, and Task records the lifecycle of short-lived work. Docker Compose service connections shorten the local feedback loop without baking addresses into code. In production, Actuator exposes operational endpoints and aggregate health, Micrometer records business measurements, and the Observation API can produce correlated metrics and OpenTelemetry spans. Trace and span identifiers connect logs to distributed traces. For constrained or rapidly scaled workloads, Spring's AOT engine supplies GraalVM with the reflection, resource, proxy, and serialization hints required by the closed-world model. Native images trade build time and some peak optimization for low startup and memory use; CRaC instead restores a warmed JVM from a coordinated checkpoint. Buildpacks package either approach into a reproducible container image.

These child topics form one lifecycle. Configuration decides which components exist. Interfaces and messages expose their behavior. Persistence and transactions protect state. Security constrains who can invoke an operation. Tests verify each boundary before deployment. Cloud infrastructure locates and connects instances, while telemetry and health reveal whether the assembled system behaves as intended. Native compilation, checkpoint restoration, and container packaging then change how quickly and efficiently the same application can be started. Treating that lifecycle as a set of connected, focused topics preserves Spring Boot's productivity without confusing framework defaults with architectural decisions.
