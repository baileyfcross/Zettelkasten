# JavaFX Application Development

Parent topic: [[Software Engineering]]

JavaFX Application Development is the chapter-level topic for building modern Java clients across desktop, mobile, embedded, web-connected, and scientific environments. Full Notes link to one of the focused child topics rather than directly to this chapter tag.

## Overview Chapter

A modern JavaFX client begins with an architectural decision about where interaction, computation, and distribution belong. [[JavaFX Application Architecture]] treats the application as more than a window containing controls. The JavaFX runtime creates the application object, establishes the JavaFX Application Thread, supplies a primary stage, and calls the application's start method. A scene is installed in that stage, and its root opens a strictly hierarchical scene graph in which each node has one parent and participates in rendering only after it is attached. Local coordinate systems and nested layout panes turn that hierarchy into a responsive interface without forcing every child to use fixed positions. Events and transitions then add behavior over the same nodes. Because the UI model is single-threaded, event handlers and animation must remain brief; background work returns only its presentation updates to the FX thread.

The framework becomes reactive through [[JavaFX Reactive UI Composition]]. FXML describes a view as a declarative hierarchy of containers, controls, properties, identifiers, and event connections. A controller receives selected nodes and supplies behavior, while Scene Builder edits the same FXML visually. Beneath the view, JavaFX properties expose observable state. An invalidation listener can defer recomputation until a value is requested, whereas a change listener receives old and new values and therefore makes evaluation eager. Subscription objects simplify listener cleanup. Unidirectional and bidirectional bindings express dependencies directly, and computed bindings cache their results until an input invalidates them. Observable lists, maps, sets, and arrays extend the same event model to collections, allowing a control to remain synchronized with a changing data model.

[[JavaFX Controls and Styling]] turns that state into an operable interface. Controls inherit node capabilities such as layout, transformations, effects, and input handling while presenting higher-level APIs. Labels and buttons share labeled behavior; toggle groups coordinate persistent choices; text formatters filter edits and translate between displayed text and typed values. Containers add collapsible, scrollable, split, tabbed, or paginated navigation. List, tree, table, and tree-table views use reusable cells and factories so large data sets can be displayed without creating a permanent visual node for every item. Selection and internal focus remain distinct models. CSS keeps presentation separate from control behavior through style classes, IDs, descendant selectors, pseudo-classes, gradients, image patterns, looked-up colors, shadows, and themes derived from the Modena stylesheet or observable platform preferences.

When a scene needs dense custom imagery, [[JavaFX Graphics and 3D]] supplies two complementary rendering models. Ordinary shapes are retained nodes whose properties and dirty regions are managed by the scene graph. Canvas is one immediate-mode node whose graphics context writes into a buffer, making it useful for large particle populations, fractals, and simulations whose individual elements do not require node identity. A timed drawing loop updates model state and repaints, while costly calculations run away from the UI thread. For three-dimensional work, JavaFX provides spheres, boxes, cylinders, custom triangle meshes, orthographic and perspective cameras, ambient and point lights, Phong materials, texture maps, and picking results for interaction. FXyz builds additional primitives, importers, and scientific visualization components on those foundations.

An application reaches users through [[JavaFX Deployment and Platform Integration]]. Existing Swing systems can host a full JavaFX scene in `JFXPanel`, and JavaFX can preserve a needed Swing component through `SwingNode`; each toolkit retains its own UI thread. For new distributions, `jpackage` bundles application code, dependencies, resources, and a tested runtime into a platform installer. GraalVM Native Image instead compiles reachable Java code ahead of time, which requires explicit treatment of reflective classes, JNI, and resources. GluonFX applies that model to iOS and Android, where shared Java and observable models can be paired with touch-oriented styles and mobile services. On Raspberry Pi, architecture-matched JavaFX libraries can render under Wayland or X11, use Monocle and DRM without a window manager, receive remote deployments over SSH, or run an AArch64 native image. A GPS navigation example demonstrates the complete embedded path from sensor readings to an interactive map.

Finally, [[JavaFX Web Cloud and Data Applications]] connects the client to external information and computation. WebView and WebEngine render HTML content, expose browsing history and loading progress, and bridge JavaScript with Java. A richer cloud client can instead call a shared REST API, convert results into Java objects, and display them through native controls while protecting service credentials behind suitable middleware. The same separation lets DeepLearning4J and ND4J perform numeric or neural-network work while JavaFX supervises training, captures drawings, overlays object detections on video, or visualizes scientific results. JShell can combine ND4J calculations with compiled JavaFX plotting helpers for rapid exploration. Space-trajectory and quantum-computing examples show the general pattern: domain computation remains in its technical library, while the client supplies immediate, interactive representations that help a person understand and direct the work.

Across all six topics, JavaFX is a coordination layer between state, presentation, computation, and delivery. The scene graph provides structure, observables make relationships explicit, controls and CSS make those relationships usable, graphics APIs handle specialized imagery, packaging carries the program to its target, and service or scientific libraries extend what the client can do. The framework's central constraint—the ownership of live UI state by the JavaFX Application Thread—also becomes its organizing principle: expensive or remote work proceeds elsewhere, and the client turns completed results into coherent visual state.
